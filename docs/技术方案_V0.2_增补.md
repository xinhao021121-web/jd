## 一、选型新增

| 用途 | 选型 | 理由 | 备选与取舍 |
|------|------|------|-----------|
| PDF 文本层提取 | `pdfjs-dist` | 浏览器端最成熟的 PDF 解析库，自带 worker，解析不阻塞主线程 | 服务端解析需引入 Node 侧 PDF 库并改造 Workers 部署形态，且会让简历文件离开本机 |
| docx 解包 | `fflate` | 体积小、无依赖；我们只需要正文文本，不值得为一行调用引入重型库 | `mammoth.js` 一行调用即可，但体积大且会把图片转成 base64 白占内存 |
| docx XML 解析 | 浏览器内置 `DOMParser` | 无需依赖；`<w:p>` 分段、`<w:t>` 取文本足够覆盖简历正文 | 第三方解析器会引入 XML 语法之外的额外规则 |
| 图片压缩 | 浏览器内置 `createImageBitmap` + `canvas.toBlob` | 无需依赖；移动端截图常见 EXIF 方向问题，`imageOrientation: 'from-image'` 可一并处理 | 服务端压缩会让原图离开本机 |
| 编码兜底 | 浏览器内置 `TextDecoder` | 中文 txt 常见 GBK，UTF-8 严格模式解码失败时回退 | 不处理会直接把乱码写进简历草稿 |

**结论：不新增服务端依赖、不新增 API Key、不新增部署形态。** 简历解析全部在浏览器内完成；图片识别沿用现有的 DeepSeek 密钥与 OpenAI 兼容客户端。

## 二、模块与落点

划分原则沿用 V0.1：**能在 Node 里跑的逻辑下沉 `packages/core`，碰文件与浏览器 API 的薄适配层留在 `apps/web`**。薄适配层不写单测，由端到端覆盖。

| 位置 | 新增内容 | 关键约束 |
|------|---------|---------|
| `packages/core` | `sniffFileType(bytes)` | 按 magic number 判断 pdf / docx / text / unknown，不信任扩展名与 MIME |
| `packages/core` | `decodeTextFile(bytes)` | 先 UTF-8 严格解码，失败回退 GBK |
| `packages/core` | `rebuildPdfText(items, opts)` | 输入已提取的 text item 数组（含 x / y / width / page），输出重排后的纯文本：按 y 聚类成行、行内按 x 排序、按间距补空格、按句末标点合并段落、按 x 间隙识别双栏 |
| `packages/core` | `assembleDocxParagraphs(paragraphs)` | 输入已提取的段落数组，做空行压缩、号码与项目符号规整 |
| `packages/core` | `sanitizeOcrText(text)` | 去掉代码块包裹与「以下是识别结果」类前缀，压缩空行，超长截断 |
| `packages/core` | `hasUsableTextLayer(text)` | 判断 PDF 是否真的提取到可用文本层：替换字符占比过高或几乎没有中英文数字时按「无文本层」兜底，不把乱码灌进草稿 |
| `packages/shared` | 错误码与常量 | 新增 `UNSUPPORTED_FILE` / `FILE_TOO_LARGE` / `NO_TEXT_LAYER` / `PARSE_EMPTY` / `VISION_FAILED` / `VISION_EMPTY`；常量 `MAX_RESUME_FILE_BYTES = 10MB`、`MAX_IMAGE_BYTES = 5MB`、`MAX_IMAGE_EDGE = 1600`、`IMAGE_JPEG_QUALITY = 0.8` |
| `packages/llm` | `vision.ts`：`buildVisionMessages(rule, imageDataUrl)` | 规则写 system、文本与图片写 user；返回 OpenAI 兼容的 content blocks |
| `packages/llm` | `createLlmClient` 泛化 | baseUrl / model 由调用方传入，视觉与文本共用同一实现；默认视觉模型 `deepseek-flash` |
| `apps/api` | `routes/vision.ts`：`POST /api/vision` | 复用现有 Zod 校验、限流、用量计数与脱敏日志；不落盘、不写正文 |
| `apps/api` | `env.ts` 新增 `DEEPSEEK_VISION_MODEL` | 默认 `deepseek-flash`，与 `DEEPSEEK_MODEL` 并列，密钥共用 |
| `apps/web` | `utils/import/` | `pdf.ts`（pdf.js 动态加载 + 提取 text items）、`docx.ts`（fflate + DOMParser）、`text.ts`（读取与编码）、`image.ts`（压缩与校验），每个文件只做 I/O 与库适配 |
| `apps/web` | 导入状态 | 解析中 / 识别中 / 校对态属于瞬时状态，**不进 localStorage**，与「生成结果不持久化」一致 |

## 三、接口契约

> V0.1 里「服务端只有一个路由」的描述由本增补覆盖：现有两条业务路由 `POST /api/llm` 与 `POST /api/vision`，共用同一套 Zod 校验、IP 限流、每日用量与脱敏日志。

### 3.1 POST /api/vision

```
POST /api/vision
Content-Type: application/json

{
  "image": "data:image/jpeg;base64,..."
}
```

| 项 | 约定 |
|----|------|
| 入参 | 单张图片的 data URL；`image` 必填，长度上限按 32 MiB 图片折算 |
| 出参 | `{ "text": "识别出的 JD 原文", "elapsedMs": 3200 }`，非流式 |
| 为什么单张 | 前端逐张调用，便于逐张显示进度、单张失败可单独重试；请求体也始终远小于 48 MiB 上限 |
| 为什么非流式 | 识别结果要整体回填给用户校对，逐字渲染没有价值 |
| 超时 | 服务端 15 秒上限（PRD 目标为单张 ≤8 秒，实测后再收紧），超时返回 `VISION_FAILED` |
| 限流 | 沿用现有 IP 每分钟 10 次与每日 100 次，**不单独计数**（成本见第四节） |
| 日志 | 只记任务类型、耗时、IP 哈希、图片字节数与结果状态，不记图片内容与识别文本 |

### 3.2 新增错误码

| HTTP | code | 场景 | 前端文案 |
|------|------|------|---------|
| 400 | `UNSUPPORTED_FILE` | 简历文件格式不在支持范围 | 暂不支持该文件格式，请导入 PDF、Word、TXT 或 Markdown 文件 |
| 400 | `FILE_TOO_LARGE` | 文件或图片超过体积上限 | 文件超过 10MB，请压缩后重试（图片为 5MB） |
| 422 | `NO_TEXT_LAYER` | PDF 无文本层（扫描件） | 这份 PDF 没有可提取的文字，可能是扫描件 |
| 422 | `PARSE_EMPTY` | 解析结果为空或过短 | 没有从文件里读到内容，请确认文件内容后重试 |
| 502 | `VISION_FAILED` | 视觉调用失败或超时 | 图片识别失败，可重试一次，或直接粘贴 JD 文本 |
| 502 | `VISION_EMPTY` | 识别结果为空 | 没有识别到文字，建议截取更清晰的范围 |
| 502 | `VISION_UNAVAILABLE` | 请求没有到达服务端（断网、服务未启动、路由不存在） | 图片识别暂不可用，直接粘贴 JD 文本不影响生成 |

> `UNSUPPORTED_FILE` / `FILE_TOO_LARGE` / `NO_TEXT_LAYER` / `PARSE_EMPTY` 由前端解析直接产生，`VISION_UNAVAILABLE` 由前端在请求异常时产生，**都不经过服务端**；列在这里是为了让前端文案与错误码同源。服务端只负责 `VISION_FAILED` 与 `VISION_EMPTY`。

## 四、DeepSeek 视觉调用（已核实的官方约束）

| 事实 | 内容 |
|------|------|
| 模型 | `deepseek-flash` 支持图片输入；`deepseek-v4-pro` 不支持 |
| 接入方式 | 同一个 base URL（`https://api.deepseek.com`）、同一把 `DEEPSEEK_API_KEY`、同一套 OpenAI 兼容 chat completions；content 由字符串改为 blocks 数组 |
| 消息结构 | 图片**只能放在 user 消息**里，放 system 会返回 400；因此规则写 system，图片与指令写 user |
| 格式识别 | 按文件实际内容嗅探（JPEG / PNG / GIF / WebP），不看文件名与声明的 MIME —— 前端压缩后统一输出 JPEG 即可 |
| 体积限制 | 内联 base64 计入请求体 48 MiB 上限；单图上限 32 MiB；单边最大 8192 px |
| token 计费 | 图片按尺寸折算 token，**每张上限 1024 tokens**；模型会自动缩放，大图统一缩到约 1300×1300 当量的规模 |
| detail 参数 | `low` 会先把图缩到 512×512（JD 小字会糊），**必须用默认的 original** |

**成本结论：** 每张 JD 截图最多 1024 input tokens，按 `deepseek-flash` 非高峰 $0.15 / 1M 输入 token 计，单张成本约 $0.00015，低于一次话术生成的文本成本。因此取消 PRD 增补里的「图片识别单独计数、每 IP 每日 20 次」，沿用现有的 IP 限流与每日配额即可。

## 五、前端解析要点

**PDF**

- pdf.js 的 worker 通过 Vite 的 `new URL('pdfjs-dist/build/pdf.worker.mjs', import.meta.url)` 引入，避免产物里 worker 路径失效；
- 逐页 `getTextContent()` 取 items，交给 `rebuildPdfText` 重排；分栏判定沿用「同一行内 x 间隙超过页宽 15%」这一条启发式；
- **中文乱码检测**：统计替换字符 U+FFFD 比例与 CJK 字符占比，异常时判定为「无有效文本层」，走 `NO_TEXT_LAYER` 兜底而不是把乱码灌进草稿；
- 限制处理页数（默认前 10 页），超限只提示不报错。

**docx**

- `fflate.unzipSync` 取 `word/document.xml`，`DOMParser` 遍历 `<w:p>` 分段、`<w:t>` 取文本、`<w:br>` 与 `<w:tab>` 转成换行与空格；
- 页眉页脚、文本框、图片中的文字不处理，解析结果里丢失属预期。

**已知边界**

- 未内嵌 ToUnicode 的 CJK 标准字体 PDF（多为扫描件以外的老式排版）需要额外打包 pdf.js 的 cmaps（约 2MB），本期不引入：这类文件会走 `NO_TEXT_LAYER` 兜底，提示改用 Word 或粘贴文本，不会把乱码写进草稿；
- 小标题短于 12 字且上一行没有句末标点时被识别为标题、独立成行；超过该长度的小标题仍可能被并进上一行，区块识别预览会把这种情况暴露给用户。

**通用**

- 文件类型先走 magic number 校验，再进入对应解析分支；
- pdf.js 与 fflate 都用动态 `import()`，只在用户点击导入时加载，首屏预算（页面加载 ≤2 秒）不受影响；
- 压缩后图片统一 `image/jpeg`、长边 1600 px、质量 0.8，约 200–500 KB。

## 七、变更分级与风险

按 `docs/项目评审标准_V0.2.md` 的日常变更门槛，本次属于 **B 类**（界面与交互 + 新增一条不触碰生成提示词与合成逻辑的路由）：必跑 `pnpm test:all` 与 `pnpm test:e2e`，不需要重跑真实模型质量回归。

| # | 风险 | 缓解 |
|---|------|------|
| 1 | 中文 PDF 提取乱码 | 乱码检测 + `NO_TEXT_LAYER` 兜底，不把乱码写入草稿 |
| 2 | 双栏或复杂版式重排错误 | 预览阶段让用户自己核对；区块识别预览会暴露小标题丢失 |
| 3 | 识别错字污染生成结果 | 识别结果只回填到 JD 输入框并进入校对态，不直接触发生成 |
| 4 | 首屏体积被解析库拖大 | 动态 `import()` + 体积回归断言 |
| 5 | `deepseek-chat` 模型名 | 官方现列模型为 `deepseek-flash` 与 `deepseek-v4-pro`，现有 `.env` 用的是旧名，需单独验证是否仍被接受 |
