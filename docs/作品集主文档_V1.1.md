## 一句话

给求职者的工具：粘贴一段岗位 JD，用已保存的简历生成 3 条可直接发送的打招呼话术，以及逐条可采纳的简历改写建议；改完的简历可以**按原文件的排版**导出。所有内容必须能在简历原文找到依据——**编造即失败**。

## 一、问题与目标用户

求职者在直聊类平台主动投递时有两件重复劳动：

1. 逐条写打招呼：复制同一段会被招聘者一眼看出模板，手写一条要 5–10 分钟，而招聘者通常只读前两句；
2. 为每个岗位改简历：成本高于打招呼本身，多数人干脆一份通用简历投所有岗位。

现有通用 AI 写作工具的两个问题：要用户自己调提示词；倾向产出「贵公司岗位非常感兴趣」这类无信息量套话，甚至编造简历里没有的经历和数字。

**目标用户**：互联网技术岗与产品岗的主动投递者——JD 硬性要求明确（技术栈、年限、业务领域），与简历的对照关系最清晰，最容易验证生成质量。

**目标**：从粘贴 JD 到复制一条敢直接发送的话术 ≤ 30 秒。

> 依据强度：以上来自自身场景与公开讨论的推演，**尚无访谈或问卷的一手数据**——见第七节第 1 条。

## 二、四条关键决策

### 1. 不信任模型：把不可让渡的规则放在模型外面

简历里的个人信息和教育经历绝不允许被改写。最直接的做法是写进提示词；我没有这么做——模型是不可靠的执行者，它可能因为上下文长度、措辞变化或版本升级而越界，而且越界是静默的。

最终方案：模型只输出「原文 → 建议写法」的片段，**替换由本地确定性代码执行**。建议锚点匹配不上就丢弃，锁定区块按原文输出。这样"个人信息与教育经历逐字不变"从一个依赖模型自觉的期望，变成了一条普通单元测试。

同一条思路后来推进到话术上：**"无编造、去套话"也由本地逐条自检并提示**，模型不再被要求「输出前自检字数与数字」——那是它做不到、也无法被验证的自审。自检命中只标注不丢弃，用户仍能拿到 3 条完整话术并自行修改。

> 代价：模型不能做整段重写，改写风格偏保守。我认为这个交换值得——求职者被追问经历时对不上，是产品事故。

### 2. 先建评测，再调提示词

第一轮真实模型回归，8 组样本里违规 11 条。逐条归因后发现三类问题：提示词只写了长度区间却没强调下限；检查器把「2022.06」误判为编造；模型会把 JD 里的「3 年以上经验」写成用户自己的年限。

分别对应三种处置：提示词明确下限并给出目标字数；检查器区分年份与年限；提示词明令禁止引用 JD 的年限。修正后两轮共 48 条话术，剩余 2 条长度越界，条级合格率 95.8%。

**这套归因链比"效果变好了"有用**：每次改提示词，回归脚本会告诉你哪条规则退化了。

### 3. 把"复制率"从条级改成会话级

原目标写的是"零修改直接复制率 ≥ 50%"，口径是被复制话术中未经编辑的比例。这个数天然接近 1/3——用户在 3 条候选里挑 1 条发送，等于要求每 2 条就有 1 条不用改，高于证据水平，会把一个健康的产品判成不达标。

改为：**会话级 ≥ 80%**（一次生成中至少有一条未经编辑被复制，回答"这一次有没有拿到敢发的话"），条级 40% 降为质量辅助线。指标口径改了，但产品范围没变。

### 4. 导出的保真度不靠重新排版，靠原地回填

用户要的是「和原来排版一样」的简历：换成平台通用模板，招聘者一眼就能看出是套模板。最直觉的做法是把简历解析成结构化数据再重新渲染成文档，但那是**重排**——字体、页边距、表格、图片、页眉页脚都得重新对齐，误差不可控。

最终选的是相反的方向：**原文件当模板，只替换被采纳建议所在的那几行文字，其余字节原样保留**。一条建议都没采纳时，导出结果与原件逐字一致，这条有单测钉住。

同一思路下否决了两条看起来更省事的路：先把 PDF 转成 Word 再导出（转换本身是版面重建而不是还原，同一份 PDF 用不同工具转出来的结果并不相同，导出结果不可预测，且浏览器端没有可靠实现），以及在原 PDF 上覆盖改写（要嵌入中文字体，与「导出不触网」冲突；改写让文字变长还会溢出原行）。结论是**只支持 Word 来源的保真导出**，PDF 与粘贴来源改为引导用户导入 Word 原件，需要 PDF 时由用户在本机另存为。

> 代价：只有导入过 Word 的用户能用到保真导出，且模板只留在内存、刷新后失效。这是为「文件不出本机」付的价。

## 三、AI 能力边界

| 交给模型 | 由本地代码承担 |
|---------|--------------|
| 抽取 JD 关键要求、在简历中找证据、组织话术措辞 | 匹配分析计算（标签命中/未命中） |
| 生成改写建议的「原文 → 建议写法」片段 | 区块切分与锁定判定（未识别标题一律锁定） |
| 按 NDJSON 协议逐行流式输出 | 事实与套话自检（数字/技能溯源、套话黑名单、表情符号） |
|  | 锚点替换、定制简历合成、命名解析 |
|  | 话术序号与风格标签、简历文件解析与图片压缩 |
|  | 原文件回填与打包（只替换命中的文本节点，其余字节不动） |
|  | 复制即归档（一次生成一条历史记录，按会话标识去重） |
|  | 限流、每日配额、密钥托管 |

提示词只保留模型必须知道的产品语气与事实约束：序号、风格标签这类本地已知字段不再要求模型输出，改写建议任务也不再重复发送简历全文（样例输入 2030 字 → 1640 字）。判定规则只有一份——线上自检与离线质量回归调用同一个函数。

流式与结构化的折中：采用 NDJSON 行粒度，单行 Zod 校验通过即渲染，校验失败的行丢弃并重试一次。比真实的逐字流式简单得多，而用户感知到的差别只是打字机动画。

## 四、评测体系（实测）

| 项目 | 结果 |
|------|------|
| 事实溯源（编造率） | 8 组样本 × 2 轮，**0 例编造**（V0.2 口径，数字、技能、学历全部可在简历原文找到）；V0.3 复跑出现 1 例建议引入新技能，已被服务端本地自检标注（见质量回归第六节） |
| 套话与表情符号 | 0 例 |
| 改写建议越界 | 0 例（全部锚定在可改写区块内，未引入新数字或新技能） |
| 话术条级合格率 | 95.8%（48 条中 2 条长度越界，集中在「简短直接型」） |
| 改写长度口径 | 两轮真实回归：只加 20% 提示词约束时，31 条建议里 13 条超限（多数落在 26%~35%，最大 +50%）；改用 40% 红线复跑后归零。结论：**提示词是目标，自检是红线** |
| Word 往返一致性 | 不采纳任何建议时，导出文件的正文与原件逐字一致；导出件能被自己的导入通道重新解析（有单测与端到端各一条） |
| 自动化测试 | 348 项（单测与集成 228 + 文档一致性 104 + 端到端 16），CI 全绿 |
| 排除项 | 越界建议在服务端就被丢弃、编造内容被逐条标注，都不依赖模型自觉 |

## 五、性能与成本（已上线）

| 指标 | PRD 目标 | 实测 |
|------|---------|------|
| 首字到达 | ≤ 5 秒 | 1.09–1.28 秒（本地回归） |
| 完整结果 | ≤ 30 秒 | 1.5–2.5 秒（本地）；1.9–3.3 秒（线上，含公网往返） |
| 流式与中止 | 首字即渲染、可中止 | 通过，端到端用例覆盖 |
| Word 保真导出 | ≤ 1 秒（PRD V0.4 增补） | [待验证] 全程本地处理，尚无计时记录 |

**成本边界的处理**：限流判断先于模型调用，超限不消耗任何额度；按 IP 每分钟 10 次、每日 100 次；全局单日上限 300 次，由 Durable Object 持久化，跨实例与重新部署都不重置。

部署形态：一个 Cloudflare Worker 同时托管前端静态产物与 `/api/llm`，前端与 API 同域（无需 CORS，密钥不出服务端）；密钥存 Worker Secret，用户简历与 JD 只存在浏览器本地，服务端不落盘。

## 六、上线状态

- 线上可体验，国内直连可达（IPv6）；
- 简历、JD、定制简历存档全部保存在浏览器 localStorage，服务端只转发不存储；
- 改完的简历可按原文件排版导出为 Word（仅限 Word 来源），导出全程本地、断网可用；
- 复制过的话术自动进入「话术历史」（一次生成一条，上限 20 条），同样只存本机；
- 公开部署的单日调用上限设为 300 次，链接外传时成本有硬顶。

## 七、已知不足

1. **用户侧证据缺失**：没有访谈、问卷或竞品实测，痛点来自推演。这是当前最大的短板。
2. **评测样本是自造的**：8 组样本格式规整，没有真实简历的噪声（多栏、中英混排、排版混乱），说服力有限，计划扩到 30 组以上。
3. **核心价值指标没有真实数据**：会话级复制率（目标 ≥ 80%）与建议采纳率（目标 ≥ 70%）的口径和采集已落地——每次生成分配会话标识，复制、采纳、保存都归属到对应会话，生成页可查看并导出原始记录——但真实投递数据仍在积累中，目前为空。
4. **没有单位经济性测算**：未计算单次调用的 token 成本与单用户成本，只做了总量控制。
5. **国内直连依赖 IPv6**：IPv4 出口到 Cloudflare 的部分网段被阻断，纯 IPv4 网络需要代理。
6. **保真导出只覆盖 Word 来源**：PDF 与粘贴来源的用户只能拿到文本，需要 PDF 时得自己在 Word / WPS 里另存为；原文件模板只留在内存，刷新后要重新导入。
