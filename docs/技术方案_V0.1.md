## 一、方案目标

1. 支撑 PRD V0.2 的全部 P0 功能（简历长期资产、按 JD 改简历、定制简历存档、生成打招呼）；
2. 满足已确认的非功能口径：流式返回、首字 ≤5 秒、完整结果 ≤30 秒、每 IP 每分钟 10 次与每日 100 次配额；
3. 数据仍只保存在使用者浏览器本地，服务端不落盘；
4. 半年内公开发布不需要重构：密钥不下发前端，服务端具备限流与用量控制；
5. 模型能力可替换：DeepSeek 只是当前实现，接口按 OpenAI 兼容协议抽象。

**本方案不做的事**：账号体系、云端同步、简历文件（PDF / Word）解析、多平台适配 —— 均为 PRD 标注的后续版本范围。

## 二、技术选型

| 层次 | 选型 | 理由 | 备选与取舍 |
|------|------|------|-----------|
| 语言 | TypeScript 5 + Node 20 LTS | 前后端共用类型；PRD 要求"锁定区块逐字不变"这类约束必须有编译期与运行期双重保障 | 纯 JS 无法在没有测试的情况下守住区块锁定 |
| 构建 | Vite | 静态 SPA，冷启动快，产物可直接托管 | Next.js 的 SSR 与路由在本产品无用武之地，反而让"数据不出本地"难以解释 |
| 界面 | React + Tailwind CSS | 生态成熟，与现有 Demo 的单页结构最接近，迁移成本低 | Vue 等价可行，团队熟悉度优先 |
| 状态 | Zustand | 四个视图共享简历与 JD，跨页面同步只需一个 store；无 Provider 嵌套 | Redux 对单页工具过重 |
| 校验 | Zod | 一份 schema 同时用于模型返回校验、localStorage 反序列化与测试断言 | 手写校验无法覆盖模型输出的不确定性 |
| 本地存储 | localStorage | 原始简历 + JD + 最多 20 份定制简历，总量远小于 5MB | IndexedDB 留到 V0.3 存简历文件时再引入 |
| 服务端 | Hono + @hono/node-server | 只有一个路由，Hono 体量小且 runtime 无关，日后要迁 Cloudflare Workers 只换 adapter | Fastify 同样可行，但迁 Workers 需要重写启动层 |
| 模型 | DeepSeek（OpenAI 兼容） | 中文简历与 JD 场景效果好、价格低、支持流式与 JSON 输出 | 通义 / Kimi 通过同一 client 抽象可平滑切换 |
| 包管理 | pnpm workspaces | 单仓库多包，前后端共享 `core` 与 `llm` | 单包工程无法隔离纯逻辑与运行时依赖 |
| 单元测试 | Vitest | 与 Vite 共用配置，纯函数测试无需额外构建 | 沿用现有 `node --test` 会与 TS 编译链重复 |
| 端到端 | Playwright | 覆盖 PRD 5.2.1 中标注"自动测试"的交互链路 | 仅靠单测无法验证"采纳后合成"的真实链路 |
| 部署 | 前端静态托管 + Node 服务进程，均部署在境外 | 无需域名备案，避免备案周期影响公开发布时间 | 国内服务器需备案，时间不可控 |

三个包的分工：`packages/core` 承载纯逻辑，`packages/llm` 承载模型调用与输出协议，`packages/shared` 承载前后端共用的类型与错误码。

包的边界原则：`packages/core` 不依赖浏览器、不依赖网络、不依赖模型，是纯函数库；凡是不依赖 I/O 的产品规则都放在这里，从而可以被完整单测覆盖。

## 四、总体架构

```
浏览器（apps/web）
  ├── Zustand store ── 读写 localStorage（简历、JD、定制简历存档、行为记录）
  └── fetch POST /api/llm（携带 task 与文本，流式读取）
            │
            ▼
Node 服务（apps/api，唯一路由）
  ├── 校验请求体（zod）
  ├── 限流与每日配额（每 IP 每分钟 10 次、每日 100 次）
  ├── 注入 API Key（仅服务端环境变量）
  └── 转发并流式回传
            │
            ▼
DeepSeek API（OpenAI 兼容，stream: true）
```

三条不可突破的约束：

1. **密钥不出服务端**：前端代码、构建产物、日志中都不出现 Key；
2. **服务端不落盘**：请求内容只用于转发，处理结束即释放，不写数据库、不写文件、日志不含简历与 JD 正文；
3. **产品规则不下放到模型**：区块锁定、合成、命名解析、指标计算全部由 `packages/core` 的确定性代码完成。

## 五、核心模块设计

### 5.1 packages/core（纯逻辑，测试重点）

| 函数 | 职责 | 关键约束 |
|------|------|---------|
| `parseResume(text)` | 按小标题切分简历为区块，保留原始顺序与原文 | 不确定的标题一律判为锁定 |
| `classifyBlock(title)` | 判定区块可改写或锁定 | 命中 PRD 3.3 的三张标题清单；未命中即锁定 |
| `planSuggestions(blocks, plan)` | 把模型返回的建议绑定到区块 | 建议不得跨区块、不得落在锁定区块 |
| `applySuggestions(blocks, adopted)` | 锚点替换，合成定制简历 | 原文匹配不上则丢弃该条；锁定区块逐字输出 |
| `composeCustomResume(resume, adopted)` | 对外统一入口，返回合成文本 | 未采纳任何建议时，输出必须与原件完全一致 |
| `extractJdTitle(jd)` | 从 JD 解析「公司 · 岗位」 | 按 PRD 3.4 命名规则四级回退 |
| `calcMetrics(events)` | 计算零修改直接复制率等指标 | 纯函数，输入行为记录数组 |

`applySuggestions` 是整份方案的关键点：模型只输出"原文 → 建议写法"的片段，替换由本地代码执行。这样 PRD 5.2.1 的三条自动测试（区块锁定逐字一致、未采纳即与原件一致、建议不越界）都变成普通单测，不依赖模型表现。

### 5.2 packages/llm（模型接入）

- **调用次数**：话术生成与改写建议各自只发起一次调用，不把「抽取 → 匹配 → 撰写 → 自检」拆成多次请求；
- **输出协议**：要求模型按 NDJSON 输出，每行一个完整 JSON 事件，避免增量 JSON 解析；
- **结构校验**：每行事件用 Zod 校验，校验失败的行丢弃并重试一次（对齐 PRD 2.3.1）；
- **提示词**：两种任务各一套模板，事实溯源、长度、禁用套话等规则写进系统提示，并在返回结构上要求引用简历原文片段；
- **可替换**：`createLlmClient({ baseUrl, model, apiKey })` 只依赖 OpenAI 兼容协议。

### 5.3 apps/api（唯一路由的服务端）

| 关注点 | 设计 |
|--------|------|
| 路由 | 仅 `POST /api/llm`，无其他业务路由 |
| 请求校验 | Zod 校验 `task`（`greeting` / `suggestions`）、`resume`、`jd`，长度下限 20 字，与前端校验同源 |
| 密钥 | 从环境变量读取，启动时缺失直接退出并提示，不进入任何响应 |
| 限流 | 单实例内存滑动窗口实现每 IP 每分钟 10 次、每日 100 次；部署到 Workers 时由 Durable Object 承载（`apps/api/src/cloudflare/counters.ts`），限流窗口仍在对象内存、单日用量落存储。取键的 IP 由 `apps/api/src/client-ip.ts` 统一解析：`CF-Connecting-IP` → `X-Forwarded-For` 第一跳 → `X-Real-IP` → `unknown`。CF 头排在最前是因为它由边缘写入、请求方覆盖不了，而 XFF 是追加语义、第一跳可能来自调用方；两个头都没有时所有请求落到 `unknown` 同一个桶，直连 Node 端口（无反向代理注入）时按 IP 的限额会退化成全局限额 |
| 用量告警 | 全局单日调用量跨过告警阈值写脱敏告警日志，跨过硬上限直接拒绝（`DAILY_CALL_ALERT` / `DAILY_CALL_CAP`），两者都不消耗模型调用。当日计数在**入参校验之后**自增，只统计真正会发起模型调用的请求：校验不过的请求返回 400 且不占额度，避免用无效请求打空公开部署的当日额度 |
| 超时 | 首字超过 5 秒即中止并向客户端发送错误事件；整体请求设置 30 秒上限 |
| 重试 | 仅在"模型返回无法解析"时重试一次，不重试限流与鉴权错误 |
| 日志 | 只记录错误类型、耗时、任务类型与 IP 哈希，不记录正文 |

限流触发时直接返回 429 与固定文案，不消耗模型调用；对应 PRD 5.2.1「接口防护」验收项。

### 5.4 apps/web（前端）

- **视图**：沿用 PRD 2.4 的四视图 + 可收起侧边栏，路由不入 URL，切页不刷新；
- **状态切片**：`resume`（已保存简历与编辑草稿分离）、`jd`（跨页面共享）、`suggestions`（建议与采纳状态）、`archive`（定制简历）、`ui`（侧边栏）；
- **存储**：Zustand persist 写入 localStorage，读取时用 Zod 校验，失败回退默认值并保留原始数据；
- **流式渲染**：`fetch` + `ReadableStream` 逐行解析事件；首字到达即开始渲染，生成中可中止，中止后保留已生成内容；
- **文案映射**：错误提示集中在一处常量表，与 PRD 2.3.1 一一对应。

### 5.5 数据模型（localStorage）

键名统一前缀与版本号，便于迁移：`zhipin-assistant:v1:<name>`。

| 键 | 内容 | 说明 |
|----|------|------|
| `resume` | `{ text, savedAt, charCount }` | 已保存的原始简历，唯一事实来源 |
| `jd` | `{ text, updatedAt }` | 生成话术与改简历共用 |
| `customResumes` | `{ id, name, nameEdited, jdText, content, adoptedCount, charCount, createdAt }[]` | 最多 20 份，超出移除最早 |
| `events` | `{ type, at, ... }[]` | 生成、复制、采纳、保存等行为记录 |

## 六、接口契约

### 6.1 请求

```
POST /api/llm
Content-Type: application/json

{
  "task": "greeting" | "suggestions",
  "resume": "已保存的简历原文",
  "jd": "岗位 JD 原文"
}
```

### 6.2 响应（流式）

`Content-Type: text/event-stream`，事件类型固定四种：

| 事件 | 载荷 | 前端处理 |
|------|------|---------|
| `analysis` | `{ requirements[], matched[], missing[] }` | 渲染匹配分析标签 |
| `item` | `{ kind, index, payload }` | 话术卡片或建议卡片逐条出现 |
| `done` | `{ elapsedMs }` | 结束生成，恢复按钮 |
| `error` | `{ code, message }` | 按 PRD 2.3.1 映射文案，保留输入 |

### 6.3 错误码

| HTTP | code | 场景 | 前端文案 |
|------|------|------|---------|
| 400 | `INVALID_INPUT` | 参数缺失或短于 20 字 | 请先粘贴简历和 JD 内容 |
| 429 | `RATE_LIMITED` | 超过每分钟或每日配额 | 请求过于频繁，请稍后再试 |
| 502 | `UPSTREAM_ERROR` | 模型报错或鉴权失败 | 生成失败，请稍后重试 |
| 502 | `INVALID_OUTPUT` | 重试一次后仍无法解析模型输出 | 生成结果异常，请重新生成 |
| 504 | `FIRST_TOKEN_TIMEOUT` | 首字超过 5 秒 | 生成超时，请重试 |
| 504 | `TOTAL_TIMEOUT` | 整体超过 30 秒上限 | 生成超时，请重试 |

> `INVALID_OUTPUT` 与 `TOTAL_TIMEOUT` 是落地时对 PRD 2.3.1「返回内容无法解析」「模型服务超时」两条异常场景的细分，文案与 PRD 保持一致。

## 七、关键实现要点与风险

| # | 要点 | 说明 |
|---|------|------|
| 1 | 流式与结构化的折中 | 采用 NDJSON 行粒度，单行校验通过即渲染；"逐字"由前端打字机动画呈现，不影响数据正确性。若坚持真实逐字，需引入增量 JSON 解析，复杂度显著上升 |
| 2 | 首字 ≤5 秒如何保障 | 使用非推理模型、限制输出长度、`stream: true`；服务端记录首字耗时并作为监控指标 |
| 3 | 锁定区块保障 | 不依赖模型自觉，靠 `applySuggestions` 的锚点匹配 + 单测覆盖 |
| 4 | 模型越权 | 提示词中禁止新增事实；返回结构要求带简历原文引用，便于本地校验与人工复核 |
| 5 | 成本控制 | 限流 + 每日配额 + 单日用量告警；限流判断先于模型调用 |
| 6 | 境外访问稳定性 | 部署在境外可免备案，但国内访问质量需实测；若体感差，再评估国内备案 + 国内节点方案 |
| 7 | 本地存储丢失 | 数据只在本机浏览器，清除浏览器数据即丢失；MVP 接受该风险，V0.3 可考虑导出/导入 JSON |

## 八、测试策略

| 层次 | 工具 | 覆盖内容 |
|------|------|---------|
| 纯逻辑 | Vitest | `packages/core` 全部函数；PRD 5.2.1 中标"自动测试"的六项 |
| 模型协议 | Vitest + 固定样本 | NDJSON 解析、Zod 校验、重试与丢弃逻辑 |
| 服务端 | Vitest + Hono `app.request()` | 请求校验、限流与配额、错误码映射、密钥不出现在响应中 |
| 端到端 | Playwright + 本地 mock 模型服务（`pnpm mock:model`） | 保存简历 → 生成话术 → 采纳建议 → 合成 → 存档 → 删除隔离；覆盖刷新保留与限流提示 |
| 质量回归 | 手动触发的脚本 | 8–10 组真实简历 + JD，断言数字与技能可溯源、无套话黑名单词 |
| 文档一致性 | node:test | PRD 与原型、PRD 与技术方案的关键结论一致（沿用现有做法） |

交付门槛：上述自动化测试全部通过，且质量回归的样本结论留档，才视为可交付。
