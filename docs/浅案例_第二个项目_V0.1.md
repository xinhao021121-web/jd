> **为什么要有第二个案例**：只有一份深度案例，读者无法判断这是「偶尔做成一个」还是「有可复用的方法」。第二个案例不要求开发量，要求的是**同样的判断力出现在另一个问题上**。

## 一、准入规则（先定死，避免写出一份漂亮的空壳）

1. **必须是真实做过的**：没做过的项目不写；只做过一部分的，写做过的那部分；
2. **必须有可验证的结果或明确没有结果**：「上线了」「有人用了」「某个数变了」都算，「效果很好」不算；
3. **必须有至少一处取舍**：写出你放弃的那条路，以及为什么——这是浅案例唯一真正值钱的部分；
4. **不要求开发量**：做过调研、写过方案、搭过原型、甚至只是把一个流程跑通，都可以成为浅案例；
5. **证据等级照实标**：与主案例同一套规矩——实测 / 已上线 / 待验证，不混用。

## 二、需要提供的素材（六项）

| # | 要回答的问题 | 填写要求 |
|---|------------|---------|
| 1 | 哪个项目（一句话说清它是什么、给谁用） | 20–40 字，不要形容词堆砌 |
| 2 | 真实问题是什么，你怎么知道的 | 谁遇到了什么麻烦；来源是访谈、自己的经历、还是别人的反馈——写明来源，这是证据强度 |
| 3 | 你做了什么 | 只要结果形态（方案 / 原型 / 上线 / 调研报告），不需要过程流水账 |
| 4 | **最关键的一处取舍** | 你放弃的那条路是什么，为什么不走它。这一项不能空 |
| 5 | 结果 | 有可验证结果就写具体；没有就写「没有可验证结果」——**不许编** |
| 6 | 边界 | 哪些没做、哪些没验证 |

## 四、写完之后放在哪

- **正文**：替换本文档（文件名与版本号随内容升版），结构固定为「是什么 → 真实问题 → 判断与取舍 → 结果 → 边界」五段，控制在 800 字以内——浅案例的价值在克制，写长了反而像注水；
- **入口**：在 [作品集主文档_V1.3.md](作品集主文档_V1.3.md) 的附录里加一行指向它；
- **不放进主页面的项目索引**：在 N3（作品集首页）落地时再决定它是并列展示还是作为附属；
- **不进「证据边界」表**：那是证据清单，不是项目清单，两者不要混。

## 五、这份浅案例不能支撑什么

- 不能替代主案例的深度：它出现的目的是展示**广度与一致性**，不是再讲一遍完整的方法论；
- 不能把「做过」写成「做成了」：没有结果的项目照实写没有结果，**这比编一个好结果安全得多**；
- 不能借它宣称「我有多个成功的 AI 产品」：成功的判定需要结果，而结果要照实写。
