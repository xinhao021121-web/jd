## 一、结论与范围

改完的简历要交回用户手上，且**版面必须和原文件一致**。本次只做三件事：

1. **模板留存**：导入 .docx 时把原始字节留在内存，作为导出用的模板；
2. **原地回填**：把已采纳的建议写回原文件的正文，其余内容原样保留，重新打包下载；
3. **长度约束**：改写建议的长度上限写进提示词并由本地自检标注，避免改写撑长原行。

**不新增任何依赖、不新增接口、不新增密钥、不新增部署形态。** 回填是字符串处理，打包复用已经在用的 `fflate`；导出全程在浏览器内完成，断网可用。

判断依据见第四节「被否决的方案」：PDF 转 Word 再导回、在原 PDF 上覆盖改写这两条路都试过了价值评估，结论都是不做。

## 二、模块与落点

划分原则沿用 V0.1：**能在 Node 里跑的逻辑下沉 `packages/core`，碰文件与浏览器 API 的薄适配层留在 `apps/web`**。

| 位置 | 新增内容 | 关键约束 |
|------|---------|---------|
| `packages/core` | `normalizeLineWithSpans(raw)` | 返回规整后的文本与**逐字符来源区间**，供回填时把「模型看到的文本」映射回「文件里的原文」 |
| `packages/core` | `fillDocxTemplate(documentXml, adopted)` | 输入 `word/document.xml` 原文与已采纳建议，输出改写后的 XML、命中数与跳过数；纯字符串处理，不依赖 DOM 与 zip |
| `packages/core` | `suggestionLengthLimit(before)` | 长度红线：`before + max(⌈before × 40%⌉, 5)`；提示词用的 20% 目标比例与它定义在同一处，两个口径不会漂移 |
| `packages/web` | `utils/export/docx.ts` | `exportDocx(template, adopted, fileName)`：`fflate.unzipSync` 解包 → 换掉 `word/document.xml` → `zipSync` 打包 → 触发下载 |
| `packages/web` | `utils/download.ts` 新增 `downloadBlob` | 与 `downloadJson` 并列；导出的文件不经过网络 |
| `packages/web` | 导入适配层返回模板 | `parseResumeFile` 从 `Promise<string>` 改为返回文本与模板字节；非 docx 来源的模板为空 |
| `packages/web` | store 新增 `resumeTemplate` | `{ bytes, fileName } | null`，**内存态，不进 localStorage**（`partialize` 不含该字段） |
| `packages/llm` | 改写提示词新增长度要求 | 与本地自检使用同一个 `suggestionLengthLimit`，规则只有一份 |

`fillDocxTemplate` 不引入 zip 与 DOM 依赖，是为了让它能在 Node 里被完整单测——`packages/core` 的覆盖率要求是 100%。

## 三、回填算法

### 3.1 为什么是字符串级替换，而不是 `DOMParser` + `XMLSerializer`

导入时用 `DOMParser` 只读解析是安全的，但**导出时不能用它做往返**：

1. `XMLSerializer` 会重排命名空间声明与属性顺序，未改动的部分不再与原文一致，「逐元素一致」的口径就守不住了；docx 对命名空间声明的位置敏感，处理不当会让 Word 报文件损坏；
2. Vitest 跑在 `node` 环境，没有 `DOMParser`，核心算法将无法单测，而核心算法的分支（跨片段、实体、定位失败）恰恰最需要单测；
3. 回填的任务本质是「替换若干段文字」，不需要理解整棵 XML 树。

因此改为：**只在字符串层面定位文本节点并替换其内容，其余字节原样保留。**

### 3.2 命名空间前缀探测

标签前缀不写死：从 XML 中探测 `http://schemas.openxmlformats.org/wordprocessingml/2006/main` 对应的前缀（`w`、其他前缀或无前缀三种情况都要支持），再据此构造匹配段落与文本节点的正则。探测不到声明时**不做任何替换**，按 `fallback` 处理，导出原文件的副本——宁可导出原件，也不要在看不懂的文件上乱改。

### 3.3 段落分组：最内层优先

按标签出现顺序扫描一遍，维护段落栈：

- 遇到段落开始标签入栈，结束标签出栈，该段落块完成；
- 文本节点归属**栈顶（最内层）**段落块。

嵌套只出现在文本框（`w:txbxContent`）里。导入解析时外层段落会连带收集文本框内的文字，回填时不沿用这个口径——文本只归属最内层段落，**绝不重复修改、绝不误改**，未识别或看不懂的结构一律按「不改」处理，与既有「宁可少改也不越界」一致。

### 3.4 规整坐标映射：导入与导出必须用同一套规则

导入时 `normalizeParagraphLine` 会规整文本（`•` 转 `- `、全角空格与 `\u00a0` 转半角、编号写法统一、连续空格压缩、首尾去空）。模型看到的是**规整后**的文本，它返回的 `before` 因此在原文件里可能并不存在——原文是 `• 负责订单系统`，模型返回的是 `- 负责订单系统`，直接搜必然失败。

解决办法是让规整过程同时产出**逐字符的来源区间**：

```
normalizeLineWithSpans('• 负责订单') =>
  text : '- 负责订单'
  spans: [[0,2],[0,2],[2,3],[3,4],[4,5],[5,6]]
         -     空格   负    责    订    单
```

即规整后每个字符对应原行文本里的哪一段。定位到 `before` 后取区间两端（`spans[s].start` 与 `spans[e-1].end`）就得到了原文的替换范围，插入产生的字符（例如 `- ` 里的连字符）用整个匹配区间作为来源，替换时会连同原始的 `•` 一起被替换掉，这正是想要的结果。

**实现上不另写一套规整逻辑**：把现有 `normalizeParagraphLine` 改造为 `normalizeLineWithSpans` 的薄包装，`text` 部分逐字保持不变。规则只有一份，导入与导出不可能漂移——与 V0.3 增补「线上兜底与离线回归共用同一份函数」同理。

### 3.5 文本片段分配与写回

一个段落里的文字通常被 Word 拆成多个片段（`<w:t>`，分别属于不同的 `<w:r>`），替换区间可能跨片段。做法是：

1. 建立段落内「字符位置 → 片段 + 片段内偏移」的映射，`<w:br>` 记为换行、`<w:tab>` 记为空格（与导入的 `collectText` 口径一致）；
2. 把替换区间覆盖到的片段整理成一组编辑：首个受影响片段保留前缀后写入 `after`，完全落在区间内的片段清空，末尾片段保留后缀；
3. 被替换区间覆盖到的 `<w:tab>` 一并删除（保留了反而会让新文字错位）；
4. 所有编辑按片段在 XML 中的位置**从后往前**应用，前面的偏移不会失效。

被改写文字继承首个受影响片段的格式（`<w:rPr>`），因此一行里若有句中加粗，改写后该行格式会统一——这是已知取舍，写入 PRD 二节。

### 3.6 文本内容的编解码

`<w:t>` 内容里的 `&`、`<`、`>` 是实体形式。匹配前按 XML 规则解码，写回时再编码；解码要覆盖命名实体与数字字符引用。空内容片段保留为空的 `<w:t></w:t>`，不删除节点，避免破坏其所在段落的属性顺序。

### 3.7 返回值与降级

| 字段 | 含义 | 界面处理 |
|------|------|---------|
| `xml` | 改写后的 `word/document.xml` | 打包下载 |
| `applied` | 成功写回的建议条数 | 用于埋点计数 |
| `skipped` | 在模板中定位不到而跳过的条数 | 导出完成后提示用户 |
| `fallback` | 命名空间探测失败或模板结构无法识别 | 导出原文件副本并说明未应用改写 |

## 四、被否决的方案

### 4.1 PDF 先转 Word，改完再转 PDF

| 项 | 结论 |
|----|------|
| 可行性 | 浏览器端没有可靠的 PDF → docx 实现；能做到的（Adobe PDF Services 等）都要求把文件传到服务端，与「简历文件不出本机」直接冲突 |
| 保真度 | 从 PDF 反推 docx 是**版面重建**而不是还原，同一份 PDF 用不同工具转出的 docx 并不相同，导出结果不可预测 |
| 误差累积 | 转换引入两次误差（转 docx、再转回 PDF），比不做转换更偏离原版 |
| 后半段同样无解 | 浏览器端 docx → PDF 只能渲染成 HTML 再打印，质量低于任何本机排版软件 |
| 替代 | 用户本机 Word / WPS 的「另存为 PDF」比任何浏览器方案都好，交给用户做 |

### 4.2 在原 PDF 上覆盖改写

PDF 覆盖层（pdf.js 取文字位置 + 覆盖绘制新文字）在**版面保真**上其实优于回填 Word，但被两件事挡住：

1. **离线要求**：中文绘制必须嵌入字体，需要额外准备并分发数 MB 的字体文件，与「导出不触网」冲突；
2. **溢出风险**：改写让文字变长就会溢出原行，方案直接失效，而 docx 回填由 Word 自行重排，不存在这个问题。

因此本期只做 Word 路线。改写长度约束对 Word 路线是体验优化，对 PDF 路线才是硬约束。

## 五、前端集成要点

**模板留存**

- 只有 .docx 来源带模板；PDF / TXT / 粘贴来源模板为空，导出入口置灰并引导导入 Word 原件；
- 模板与文件名都只放内存（`resumeTemplate`），刷新即失效；不进 localStorage、不进行为记录，与 PRD 增补 4.1 的数据边界一致；
- 模板只在「导入 → 保存简历」这条路径上写入，与草稿是否保存无关：用户导入后直接点导出，也应拿到基于原文件的副本。

**导出入口**

- 位置：「按 JD 改简历」结果区，与「保存到定制简历」并列；
- 可用条件：本次会话导入过 .docx（不要求先采纳建议，未采纳时导出结果即原件副本）；
- 失败提示：导出失败时引导改用「复制全文」，草稿与存档不受影响。

**下载**

- 新增 `downloadBlob(filename, blob)`，与 `downloadJson` 同源实现（`URL.createObjectURL` + 隐藏 `<a>`）；
- 文件名 `原文件名_定制.docx`，原文件名只用于本次下载。

**长度约束**

- `packages/llm` 的改写提示词新增一条长度要求（目标不超过原文的 20%）；
- `packages/core` 的 `checkSuggestionText` 新增「改写长度」违规项（红线 40%）；
- **两套口径是刻意的**：提示词是模型的目标、自检是拦截的红线，与话术「提示词给 120~150 的目标区间、自检按 100~160 判定」同一套做法。实测依据：只加 20% 提示词约束时，31 条建议里仍有 13 条超出（多数落在 26%~35%）；换成 40% 红线复跑后 31 条全部落在红线内，「改写长度」违规降到 0；
- 命中只标注不丢弃，与既有 `issues` 的处置方式一致。

## 七、变更分级与风险

按 `docs/项目评审标准_V0.2.md` 第五节，本次属于 **A 类**（改了提示词，并新增与锚点替换同源的写回逻辑）：必跑 `pnpm test:all`、`pnpm test:e2e` 与 `pnpm quality:samples`（真实模型），并把结论记入 `docs/质量回归_V0.2.md`。

| # | 风险 | 缓解 |
|---|------|------|
| 1 | 回填破坏文件结构，导出的 docx 打不开 | 只替换文本节点内容、其余字节不动；文件名与 `<w:t>` 结构不变；以真实样本做往返断言 |
| 2 | 导入规整与原文不一致导致替换静默失效 | 规整与映射出自同一函数，往返样本覆盖项目符号与全角空格；定位不到时计数并提示，不静默 |
| 3 | 嵌套结构（文本框）被误改 | 文本只归属最内层段落，外层不动；宁可少改 |
| 4 | 内存占用 | 模板上限即导入上限（10MB），只在会话内存在，刷新即释放 |
| 5 | 改写撑长原行导致版面走样 | 提示词与自检双重约束长度；超长只标注，用户仍可权衡采纳 |
| 6 | 用户导入后手工改了简历文本，模板对不上 | 跳过该条并计数，导出完成后明确告知跳过的条数 |
