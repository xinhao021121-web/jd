## 一、监控：看什么、阈值多少、越线做什么

采集点是 Worker 自身写出的结构化日志与 Cloudflare 控制台指标，不引入第三方监控服务。

| 指标 | 阈值 | 看哪里 | 越线动作 |
|------|------|--------|---------|
| 生成失败率 | > 5% | 控制台 Metrics 的错误数；日志 `event=error` / `invalid_input` / `rate_limited` | 先看 `errorType` 分布：`UPSTREAM_ERROR` 指向模型服务商，`RATE_LIMITED` 指向配额，必要时回滚（第四节） |
| 单日用量 | 触达 `DAILY_CALL_ALERT`（线上 100） | 日志 `event=usage_alert`、`errorType=DAILY_CALL_ALERT` | 确认是否链接外传；需要继续开放就把 `DAILY_CALL_CAP` 调高，否则保持并等次日 |
| 单日用量硬顶 | 触达 `DAILY_CALL_CAP`（线上 300） | 日志 `event=rate_limited`、`errorType=DAILY_CAP`；当日所有请求被 429 | 这是成本护栏正常生效；若属正常流量，先调低对外传播强度再评估是否上调 |
| 单 IP 限流 | 每分钟 10 次 / 每日 100 次 | 日志 `event=rate_limited`、`errorType=minute` / `day` | 少量属正常；持续刷量说明链接被滥用，配合密钥轮换（第五节） |
| 首字 / 完整耗时 | 首字 ≤5 秒、完整 ≤30 秒（回归红线 10 秒） | 日志 `elapsedMs`；`pnpm smoke:prod` 每次发布实测 | 明显劣化时先确认是否模型服务商侧波动，再决定是否回滚 |
| 健康检查 | `/healthz` 必须 200 | `pnpm smoke:prod -- --static-only` 或任意探针 | 非 200 直接回滚 |
| 静态产物 | 首页引用的 `/assets/index-*.js` 应与最近一次部署一致 | 首页 HTML | 不一致说明部署或缓存异常，重新部署 |

日志字段固定为 `{ level, event, task, ipHash, elapsedMs, attempts }`，事件类型为 `ok` / `rate_limited` / `usage_alert` / `invalid_input` / `error`。
**不含简历与 JD 正文**：`ipHash` 是加盐哈希，正文从不进日志（单测 `tests/api.llm.guard.test.ts`、`tests/api.load.test.ts` 逐条断言）。

### 采集方式的可用性（实测）

| 方式 | 命令 | 实测结论 |
|------|------|---------|
| Cloudflare 控制台（推荐） | Workers & Pages → zhipin-assistant → Metrics / Logs | 可用。国内网络下这是唯一稳定的查看路径 |
| 实时日志 | `npx wrangler@4.134.0 tail zhipin-assistant -c apps/api/wrangler.toml --format json` | **本机网络不可用**：`tail.developers.workers.dev` 被 DNS 污染、IPv6 直连超时（与 README 记录的 `*.workers.dev` 可达性问题同源）。需要在可用网络下执行 |

> 因此发布时的日志抽样以**同源实现 + 单测断言**为准（判定规则只有一份），实机 `wrangler tail` 抽样列为待补项（见评审记录行动项）。

## 二、回滚：版本级，不重建

Cloudflare 每次部署都会留下一个 Worker Version，回滚是把**上一个版本的代码与静态产物一起**切回 100% 流量，不需要重新构建。

```bash
# 1. 看当前与历史版本（每行一个 Version ID，含创建时间与作者）
npx wrangler@4.134.0 deployments list -c apps/api/wrangler.toml

# 2. 回滚到上一个 100% 版本（不带 version-id 即为上一个）
npx wrangler@4.134.0 rollback -c apps/api/wrangler.toml -y -m "回滚原因"

# 3. 验证：首页引用的静态产物 hash 回到旧值，且静态检查通过
pnpm smoke:prod -- --static-only

# 4. 修好之后重新发布
pnpm deploy:cf
```

回滚的判定标准只有一条：**首页引用的 `/assets/index-*.js` 变回旧版本**。只回 Worker 代码而静态产物没回去，说明操作没生效。

### 2026/09/21 演练记录（真实执行，非纸面）

| 步骤 | 命令 | 观察结果 |
|------|------|---------|
| 部署新版本 | `pnpm deploy:cf` | 版本 `192deda8-89fc-49b4-bdee-cea33a74fb59`，首页引用 `index-YsoFx2Ce.js` |
| 回滚 | `npx wrangler@4.134.0 rollback -c apps/api/wrangler.toml -y` | 切回 `4db4ee1e-9363-472f-875c-81bb967379e2`（2026-09-20 17:32 的版本），首页引用变回 `index-BtcSOYvN.js`，单次耗时约 3 秒 |
| 重新部署 | `pnpm deploy:cf` | 新版本 `3f8743b1-fde6-4135-9f4f-ba3eda3a3876`，首页引用回到 `index-YsoFx2Ce.js`，耗时约 22 秒 |
| 回滚点 | `git tag` | 每次发布在对应 commit 上打 tag（本次为 `v0.6.0`），Cloudflare 版本之外再留一个代码侧回滚点 |

结论：**回滚可用、可验证，代价是一次命令加一次首页检查。**

## 三、密钥与配额

| 项 | 做法 |
|----|------|
| 密钥存放 | 只在 Worker Secret（`DEEPSEEK_API_KEY`）；仓库、前端产物、日志里都不出现（`.env` 已在 `.gitignore`） |
| 密钥轮换 | DeepSeek 控制台新建 Key → `npx wrangler@4.134.0 secret put DEEPSEEK_API_KEY -c apps/api/wrangler.toml` → 旧 Key 停用 → `pnpm smoke:prod` 验证 |
| 配额调整 | `apps/api/wrangler.toml` 的 `[vars]`：`DAILY_CALL_ALERT`（线上 100）、`DAILY_CALL_CAP`（线上 300）；改完重新部署即生效，Durable Object 的计数不会因此重置 |
| 滥用处置顺序 | 调低 `DAILY_CALL_CAP` → 轮换密钥 → 必要时 `wrangler rollback` |

密钥轮换属于**公开发布前的必做项**：本次仍是内测阶段的密钥，对外传播前应先轮换（见评审记录行动项）。

## 四、复现命令一览

| 证据 | 命令 |
|------|------|
| 限流与配额压测 | `pnpm loadtest`（写出 `reports/压测_<时间>.md`） |
| 覆盖率 | `pnpm coverage`（阈值 80%，范围＝三个包 + 服务端） |
| 依赖漏洞 | `pnpm audit --registry=https://registry.npmjs.org`（国内镜像没有审计端点，必须指定官方源） |
| 线上冒烟 | `pnpm smoke:prod`（真实模型各 1 次调用；加 `-- --static-only` 可只做静态与健康检查） |
| 回滚 | 见第二节 |
