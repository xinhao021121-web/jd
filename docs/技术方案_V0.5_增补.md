## 一、结论与范围

话术历史是**在既有持久化层上加一个切片**，不做新的存储机制：

1. 新增 `greetingHistory` 切片，与定制简历存档同构（数组、容量上限、单条可删）；
2. 写入时机挂在**复制成功之后**，复用生成时就已存在的 `sessionId` 做去重；
3. 侧边栏把早先预留的占位项换成第 5 个视图。

**不新增依赖、不新增接口、不新增密钥。** 复制行为早就带着会话标识，历史只是把那次生成的内容一起落盘。

## 二、数据模型与落点

| 位置 | 新增内容 | 关键约束 |
|------|---------|---------|
| `packages/shared` | `MAX_GREETING_HISTORY = 20` | 与 `MAX_CUSTOM_RESUMES` 并列，容量口径只有一处 |
| `apps/web/store/storage.ts` | `STORAGE_KEYS.greetingHistory` 与新键读写 | 独立键，不改变既有 5 个键的结构，旧数据读取不受影响 |
| `apps/web/store/storage.ts` | `GreetingHistoryRecordSchema` | 逐条校验：坏掉的单条丢弃，其余保留（见第四节） |
| `apps/web/store/store.ts` | `greetingHistory` 切片与三个 action | 进 `partialize`（与 `archive` 同），刷新后仍在 |
| `apps/web/views/GenerateView.tsx` | 复制成功后调用 `saveGreetingToHistory` | 复制失败不写，历史失败不影响复制 |
| `apps/web/store/store.ts` | `VIEW_NAMES` 增加 `history` | 侧边栏与 `App.tsx` 的路由同步 |

**记录结构**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | `h` + 时间戳 + 随机数，与存档记录的 id 规则一致 |
| `sessionId` | string | 本次生成的会话标识，**去重键** |
| `jdText` | string | 生成时使用的 JD 原文；展示名由 `extractJdTitle` 现场解析，不冗余存储 |
| `items` | 数组，最多 3 | 每条含 `index`、`style`、`text`、`edited`；`text` 是复制时的内容（含用户编辑） |
| `analysis` | 对象或 null | JD 关键要求 / 已命中 / 未覆盖 / 是否低匹配 |
| `copiedIndexes` | number[] | 复制过哪几条（存话术的 `index`），用于回看「当时发的是哪条」 |
| `createdAt` / `elapsedMs` | number | 记录时间与当时的生成耗时 |

不存 `issues`：本地自检结果属于当次提示，回看时再展示一遍反而会让用户以为现在仍然有问题。

## 三、写入与去重

```
复制成功 → 记录 copy 埋点 → saveGreetingToHistory(index)
                              ├─ 按 sessionId 找到已有记录 → 合并 copiedIndexes、刷新 items
                              └─ 没有 → 新建记录并插到最前 → 超出 20 条时移除最早的
```

| 约定 | 说明 |
|------|------|
| 触发点 | `copyText` 成功之后。剪贴板被拒绝时不写，与 PRD「复制失败不入历史」一致 |
| 去重键 | `greeting.sessionId`。它本来就随每次生成生成、随每次复制写进埋点，正好是「这一次生成」的天然标识 |
| 更新而非新增 | 同一次生成里再复制另外一条时，只合并 `copiedIndexes` 并刷新 `items`（用户可能先编辑再复制），不产生第二条记录 |
| 重新生成 | 会换新的 `sessionId`，因此是另一条记录——与 PRD「重新生成后再复制记为一条新记录」一致 |
| 顺序 | 记录插在最前，超出上限时从尾部移除，与定制简历存档一致 |
| 失败隔离 | 整个写入包在 try/catch 里：历史写失败只吞掉异常，不复用影响复制成功的提示 |

## 四、容错

既有 `readKey` 的粒度是**整切片**：任何一条不合法就整份回退为默认值并另存 `:invalid`。对简历而言这是对的（宁可让用户重填，也不要半份简历），但历史记录是**可丢弃的旁路数据**，一份坏记录不该带走其余 19 条。

因此 `GreetingHistorySliceSchema` 用逐条校验：

```ts
z.array(z.unknown()).transform((items) =>
  items.flatMap((item) => {
    const parsed = GreetingHistoryRecordSchema.safeParse(item);
    return parsed.success ? [parsed.data] : [];
  }).slice(0, MAX_GREETING_HISTORY)
)
```

整份不是数组（例如被手改成对象）时仍然走 `readKey` 的常规回退。存储不可用（隐私模式）时沿用既有内存退化，刷新即失，不阻断生成与复制。

## 五、界面接入

| 项 | 做法 |
|----|------|
| 导航 | 侧边栏「后续规划」分组里的「话术历史」占位换成正式项（`data-view="history"`），分组只留「设置」；导航项右侧显示记录条数，与「定制简历」的条数展示同构 |
| 视图 | 新页面 `HistoryView`，沿用定制简历存档的「左列表 + 右详情」布局，降低认知与实现成本 |
| 列表 | 记录名称（`extractJdTitle`）、生成时间、已复制条数，按时间从新到旧 |
| 详情 | 三条话术（风格标签、字数、已编辑 / 已复制标记）、匹配分析、对应 JD；每条话术一个复制按钮 |
| 清理 | 删除单条（`data-del`，悬停出现，二次确认）与清空全部（页头次按钮，二次确认） |
| 空态 | 说明「复制过的话术会自动保存到这里」，并给去生成页的按钮 |

## 六、测试策略（在既有基础上新增）

| 层次 | 覆盖内容 |
|------|---------|
| store 单测（Vitest） | 首次复制新建记录、同一次生成再次复制只合并不新增、重新生成后是新记录、超 20 条移除最早的、删除单条、清空全部、`greeting` 为空时调用不写空记录 |
| 存储单测（Vitest） | `greetingHistory` 进 `partialize` 且刷新后仍在；单条损坏只丢那一条；整份不是数组时回退默认值；存储不可用时退化为内存 |
| 端到端（Playwright） | 生成 → 复制 → 历史出现该条 → 再次复制同批另一条只有一条记录 → 刷新后历史仍在 → 删除后清空 |
| 端到端的限流约束 | 端到端全程共用同一套每分钟 10 次的服务端限流（PRD 4.1，且有用例专门验证它生效），因此历史用例刻意让多个断言复用同一次生成，不额外增加模型调用 |
| 文档一致性（node:test） | 本文档与 PRD V0.5 增补、既有技术方案的关键结论一致 |

## 七、变更分级与风险

按 `docs/项目评审标准_V0.2.md` 第五节，本次属于 **B 类**（新增一个持久化切片与一个视图，不触碰提示词、模型参数、锁定规则与合成逻辑）：必跑 `pnpm test:all` 与 `pnpm test:e2e`。

| # | 风险 | 缓解 |
|---|------|------|
| 1 | 新切片破坏既有本地数据 | 新增独立键，不修改既有 5 个键的结构；`readSlice` 的兼容路径有单测覆盖 |
| 2 | 历史把用户「随手试试」的话术也记下来 | 每条可删、支持清空；不做自动上传，全部留在本机 |
| 3 | 历史写失败影响复制 | 写入包在 try/catch 内，复制提示不受影响 |
| 4 | 记录里的公司名属于敏感信息 | 与既有口径一致：只在浏览器本地，不参与生成请求、不上传；PRD 4.1 已同步列入留存清单 |
| 5 | 同一次生成反复复制导致重复条目 | 以 `sessionId` 为去重键，有单测钉住 |
